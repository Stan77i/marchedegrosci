## Anomalies trouvées (rien n'a été corrigé)

### P1 — grave

**A1 · Un vendeur peut supprimer son compte en pleine commande** (PRO-02)
- Preuve : `profils-u07-scenarios.sql`, PRO-02 b. Commande S→B à l'étape « chargement » ; le vendeur appelle `supprimer_compte()` → « ok » ; la commande reste `en_cours/chargement` ; le compte est bloqué pour toujours (`banned_until = infinity`).
- Risque métier : l'acheteur reste avec une commande en route dont le vendeur ne peut plus se connecter (plus de réponse, plus de preuve, plus de litige à deux). Un fraudeur peut charger, disparaître, et l'autre partie n'a plus personne en face.
- Correctif recommandé : dans `supprimer_compte`, refuser tant qu'une commande est `a_confirmer`, `en_cours` ou `litige`, ou `terminee` non clôturée (« Terminez ou annulez d'abord vos commandes »). Même règle pour une négociation conclue sans commande.
- Test de non-régression : rejouer PRO-02 b ; attendu : refus, commande inchangée, compte actif.

### P2 — gênant, à traiter avant l'ouverture

**A2 · Le quota de 3 annonces gratuites se contourne** (SEC-05 c)
- Preuve : un non-vérifié dont `annonces_publiees.n = 3` reçoit VERIFICATION_REQUISE pour une 4e annonce, mais `update offres set product_slug = 'igname', …, status = 'active'` sur une ancienne annonce retirée est accepté (compteur reste 3).
- Risque : publications illimitées dans le temps sans vérification (multi-comptes, arnaques).
- Correctif : dans `garde_publication` (UPDATE) ou `_annonce_regles`, compter comme nouvelle publication une remise en ligne qui change le produit, ou interdire de changer le produit d'une annonce retirée. À trancher par le propriétaire : « 3 annonces au total » ou « 3 en même temps » ?
- Test : rejouer SEC-05 c ; attendu : refus ou compteur à 4 et refus.

**A3 · Les données du profil restent en base après la suppression du compte** (PRO-02 b)
- Preuve : après `supprimer_compte`, `bio`, `activites`, `structure_nom` sont toujours là (prénom, nom, pseudo, avatar, ville sont vidés). `profil_public` renvoie NULL : plus visibles, mais conservés.
- Risque : vie privée (données qu'un membre croit effacées), image de marque.
- Correctif : vider aussi `bio`, `activites`, `photos`, `structure_type`, `structure_nom`, `structure_logo`, `structure_preuves` (et les fichiers liés), ou documenter pourquoi on les garde.
- Test : rejouer PRO-02 b ; attendu : ces colonnes vides.

**A4 · La levée d'un bannissement ne laisse aucune trace** (ADM-01, n° 4)
- Preuve : `admin_lever_bannissement` efface la ligne `bannis` ; `admin_journal` +0. Qui a levé, quand, pourquoi, et le motif d'origine sont perdus.
- Risque : impossible de contrôler l'équipe (complicité, erreur), impossible de savoir qu'un compte a déjà été banni.
- Correctif : écrire une ligne dans `admin_journal` (admin, cible, motif obligatoire, motif d'origine) avant d'effacer, ou garder la ligne avec `leve_le`/`leve_par`.
- Test : rejouer ADM-01 ; attendu : `journal+1` à l'étape 4.

**A5 · Une décision d'identité peut être changée sans historique** (ADM-01 n° 5, PRO-04)
- Preuve : `admin_identite_decider` « verifie » puis « refuse » sur le même dossier : accepté, la 1re décision est écrasée, rien dans `admin_journal`.
- Risque : badge « Identité vérifiée » donné puis retiré (ou l'inverse) sans preuve ; pas de contrôle de l'équipe.
- Correctif : refuser une 2e décision sur un dossier déjà décidé (passer par un nouveau dossier), ou journaliser chaque décision.
- Test : rejouer PRO-04 b ; attendu : refus de la 2e décision ou `journal = 2`.

**A6 · L'administrateur peut juger un litige où il est partie** (ADM-02)
- Preuve : commande dont le vendeur est ADM ; `admin_litige_clore(…, 'terminee', 'Je me donne raison', 'acheteur')` → accepté.
- Risque : conflit d'intérêts (le compte officiel peut vendre ; un autre admin pourrait aussi acheter ou vendre).
- Correctif : dans les fonctions qui tranchent (`admin_litige_clore`, `admin_litige_trancher2`, `admin_commande_issue`, `admin_refus_trancher`, `admin_litige_partager`, `admin_liberer`), refuser si `auth.uid()` est vendeur, acheteur ou transporteur de la commande.
- Test : rejouer la fin d'ADM-02 ; attendu : refus.

**A7 · La table `commandes` accepte des valeurs impossibles** (BDD-02)
- Preuve : écritures directes acceptées : quantité -5 et 0, prix 0, montant négatif, montant ≠ quantité × prix, vendeur = acheteur, « terminee » sans `termine_le` (elle ne serait jamais clôturée automatiquement), unité vide.
- Risque : la seule défense est dans les fonctions ; une fonction future boguée ou un script d'administration peut créer une commande fausse (montant, commission calculée sur un montant faux).
- Correctif : contraintes `check (quantite > 0)`, `check (prix_unitaire > 0)`, `check (montant >= 0)`, `check (vendeur_id <> acheteur_id)`, `check (etat <> 'terminee' or termine_le is not null)` ; ajouter `not valid` puis `validate` après contrôle (BDD-04 montre 0 ligne fautive sur le test ; à vérifier en production).
- Test : rejouer BDD-02 ; attendu : « ACCEPTÉS par la base : aucun ».

**A8 · Des avis restent comptés sur une commande annulée après litige** (BDD-04)
- Preuve : commande de simulation MDG-C-261023-FE0FD3 : terminée, avis donnés, litige, annulée par l'équipe ; les 2 avis restent ; `reputation_publique` lit `avis_commandes` sans regarder l'état de la commande.
- Risque : un acheteur met 1 étoile puis obtient l'annulation (ou l'inverse) ; la note publique ne correspond plus à une vente réelle.
- Correctif : ne compter que les avis des commandes `terminee` (jointure dans `reputation_publique`, `notes_publiques`, `mieux_notes`, `statuts_publics`), ou retirer l'avis quand la commande est annulée.
- Test : requête BDD-04 ligne « avis sur commande non terminée » + appel `reputation_publique` du vendeur avant/après.

**A9 · Aucun journal central des actions de l'équipe** (ADM-01)
- Preuve : sur 12 actions sensibles, `admin_journal` ne bouge jamais ; il n'est écrit que par 4 fonctions (numéro rendu, code changé, annonce maintenue/rétablie). Les autres traces sont dispersées dans 7 tables, sans motif pour certaines (réglages).
- Risque : un contrôle de l'équipe demande de croiser 7 tables ; un réglage changé (ex. délai de litige) n'a pas de motif.
- Correctif : une ligne `admin_journal` (admin, action, cible, motif, ancienne et nouvelle valeur) dans chaque fonction `admin_*` qui écrit.
- Test : rejouer ADM-01 ; attendu : `journal+1` à chaque action.

Correctif : clés étrangères là où l'historique n'a pas à survivre ; sinon documenter. Test : BDD-01 et lignes « orphelins » de BDD-04.
